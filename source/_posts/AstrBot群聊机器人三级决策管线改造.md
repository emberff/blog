起因是一套自拟的三级决策设计：**第一级确定性规则过滤、第二级低成本触发判断（都不调 LLM）、第三级主 AI 结合上下文与人格处理**，希望把 LLM 判定从"每条消息都过一遍"收缩成"只处理规则判不了的模糊消息"。

真正核对代码之后，这套设计有三处前提不成立：**决策 AI 早就是概率门之后的第二道关、设计表里两个触发场景在代码上根本不存在、私聊管线是一个空壳**。最后落地的不是"关掉决策 AI"，而是两个保守的规则过滤器，和一整套让主 AI 学会说"这我不接"的哨兵机制。

有意思的是哨兵上线两小时半，一次都没被触发过。这个"零"本身比改动更值得记。
{% endnote %}

# 一、起因与环境

## 1.1 设计目标

原始设计分成三档，核心诉求是"不要让每条消息都去问一次 LLM"：

| 级别 | 做什么 | 是否调 LLM |
| --- | --- | --- |
| 第一级 | 过滤系统消息、重复消息、明确无需处理的事件 | 否 |
| 第二级 | 基于上下文特征做低成本触发判断 | 否 |
| 第三级 | 主 AI 结合完整上下文与人格处理 | 是 |

设计里还有一句关键原则：**不要把"没有明确触发关键词"等同于"不需要回复"**。后面所有的反复，基本都绕这句话展开。

## 1.2 环境

| 项目 | 版本 / 说明 |
| --- | --- |
| 聊天机器人框架 | AstrBot 4.29.3 |
| 群聊增强插件 | `astrbot_plugin_group_chat_plus` V1.2.3.hotfix.2 |
| 运行时 | Python 3.12.15 / asyncio（单事件循环） |
| 模型上游 | OpenAI 兼容网关，DeepSeek 系模型 |
| 部署 | Docker + 单容器 `astrbot`，插件目录挂载在数据卷内 |
| 本文博客框架 | Hexo 8.1.2 + hexo-theme-fluid 1.9.9 |

## 1.3 可用数据

| 数据源 | 用途 |
| --- | --- |
| `docker logs astrbot`（24h / 72h） | 判定次数、yes/no 分布、token 消耗、各路径拦截量 |
| 插件源码 `main.py`（改造前 15,069 行，改造后 15,096 行） | 分流路径、状态副作用、插入点定位 |
| 配置文件 364 个键 | 判定相关开关的实际取值 |

一个必须先钉死的前置事实：**日志里的 `main:NNNN` 行号是运行时代码的行号**。插件经历过多次改写，历史日志里的行号带着 +13 / +72 的不等偏移，直接拿去对当前文件会全线错位。本次改造期间又先后叠了两层补丁（第一级过滤 +77 行、哨兵 +27 行），4251 之后的所有行号整体后移——所以本文所有行号都以「两档补丁打完、15,096 行」那一版为准。

# 二、现状核对：设计假设与代码事实

## 2.1 决策 AI 不是"必经关卡"，它已经是第二道门

设计的出发点是"决策 AI 挡在每条消息前面"。实测 24 小时数据不支持这个描述：

| 指标 | 数值 |
| --- | --- |
| 平台群消息 | 505 |
| 决策 AI 调用 | 321 |
| **调用率** | **63.6%** |
| yes / no | 100（31.2%）/ 221（68.8%） |
| 每产生 1 次回复消耗的决策调用 | **3.21 次** |

中间那 36% 去哪了？被**概率筛选**（`probability_manager`）挡住了——它是纯规则 + 掷骰，一次 LLM 都不调，24 小时拦掉 177 条（占进入概率门的 47.8%）。

也就是说现状本来就是两级门，决策 AI 只是第二级。设计里"从必经关卡改成辅助组件"这个描述，方向上成立，幅度上被高估了。

## 2.2 第一级：三块已成型，缺两块

| 设计要求 | 现状 |
| --- | --- |
| 过滤无意义系统消息 | **部分**。真空消息、伪造戳一戳、撤回通知都能拦；但 JSON 卡片漏过 |
| 过滤完全重复消息 | **缺失**。只有平台 `message_id` 去重，挡不住"同一个人换 ID 反复发同一句" |
| 过滤明确不需要处理的事件 | **已实现且最完整**：指令、自身消息、未启用群、黑名单、@全体、@他人、他插件已回复 |
| 保留文本 / 图片 / 引用 | **已实现**，不需要动 |

## 2.3 第二级：四个触发项里两个不存在

| 设计要求 | 代码事实 |
| --- | --- |
| @ 希可 → 直连 | 已实现（`is_at_message` 为真时跳过判定） |
| **回复希可 → 直连** | **不存在**。`main.py` 连 `Reply` 组件都没 import，引用只被渲染成一行文本 |
| **明确讨论希可 → 直连** | 只有 `trigger_keywords`（希可/大肥鱼/哦鲸鲸）子串匹配，24 小时实测**触发 0 次** |
| 延续话题 → 尽量绕过 | 只在概率门生效，不绕决策 AI |
| 纯第三方交流 → 规则过滤 | 规则做不到。这一条是设计里最容易写、最难实现的一句 |
| 直接提问 → 直连 | 无任何识别 |

## 2.4 私聊管线是空壳

设计表第一行是"私聊：关闭决策 AI，正常消息直接进主 AI"。核对后发现 `private_chat/private_chat_main.py` 的函数体首行就是 `return`，日志文案写的是"还没做完"。而 `enable_private_chat` 本身也是 `false`。

**私聊不处理任何消息**，不是"关闭决策 AI 后直连主 AI"。这一条被单独立项，本次不碰。

## 2.5 关键词命中却仍然去问决策 AI

这是最容易被忽略的一处浪费。判定入口的条件是：

```python
should_do_ai_decision = not is_at_message and (
    not has_trigger_keyword or keyword_smart_mode
)
```

`keyword_smart_mode` 当前为 `true`，于是**命中触发关键词的消息照样走进 LLM 判定**——明明已经被点名了，还要再问一次"要不要回"。

24 小时里这类消息有 54 条，占全部决策调用的 **16.8%**。

# 三、真正的问题

## 3.1 一张卡片换来 16,646 个 token

平台下发的 JSON 卡片（小程序分享、ark 消息）没有自然语言内容，但原链路会照常把它送进决策 AI。

线上实证：

```
on_group_message → 概率通过 → 决策AI prompt_tokens=16646
→ 模型自述「当前消息是 [ComponentType.Json]，没有实际文本内容」→ 回 no
```

**16.6k token 换一个必然的 no。** 单条量小，但这类消息在群里出现时往往成片。

## 3.2 复读刷屏没有任何过滤

平台 `message_id` 去重只挡"同一条消息被重复推送"。如果同一个人换着消息发同一句话，原链路一条都拦不住。

## 3.3 主 AI 没有"可以不说话"的出口

这一条在改造后半段才暴露出来。回复生成的静态提示词里写着：

> 你的任务：直接生成回复内容。系统已将消息交给你处理，你**无需考虑**"该不该回复"或"该不该开口"——这些判断已经完成。

一旦规则层把更多消息直接放进主 AI，而主 AI 又被明令禁止判断"该不该说"，结果就是**进多少条就必须说多少句话**。所以让主 AI 学会拒绝，是扩大直连范围的前提，不是可选项。

# 四、修改方式与评估

## 4.1 第一级：两个过滤器的保守口径

### JSON 卡片：只丢纯卡片

判定口径是"整条消息只有一个 `Json` 组件，没有非空文本，也没有任何其它组件"：

```python
if _msg_components:
    _card_only_json = False
    _card_has_content = False
    for _card_c in _msg_components:
        if isinstance(_card_c, Json):
            _card_only_json = True
        elif isinstance(_card_c, Plain):
            if self._coerce_component_text(_card_c.text).strip():
                _card_has_content = True
        else:
            _card_has_content = True
    if _card_only_json and not _card_has_content:
        logger.info("🚫 [JSON卡片过滤] ...")
        event.call_llm = True
        return
```

带文字的卡片、带图片/@/引用的卡片、XML 与 `Unknown` 组件**一律放行**。代价是：如果适配器把卡片映射成 `Unknown` 而不是 `Json`，这个过滤器会静默失效——方向是安全的（只漏拦、不误伤）。

### 复读去重：90 秒内第 4 次才丢

第一版实现只提取 `Plain` 文本做指纹，评审时发现一个真 bug：

> 「好的 + 图片 A」「好的 + 图片 B」「好的 + 图片 C」「好的 + 图片 D」四条消息的指纹完全相同，第 4 张图会被误删。

修正后要求**整条消息只有 Plain 组件**才参与去重：

```python
_dup_text_only = bool(_msg_components) and all(
    isinstance(_dup_c, Plain) for _dup_c in _msg_components
)
```

同时窗口状态 `_dup_repeat_window` 原本只在字典超过 500 项时清理，稳定在阈值以下就会永久驻留。改成时间驱动：每 60 秒全表清理一次，仍超 1000 项则截断保留最近的。

最终口径：**同群 + 同发送者 + 同纯文本指纹**，90 秒内**第 4 次**起丢弃，前 3 次照常处理，单字消息不参与，不同发送者互不合并。

### 一个必须写对的状态：`event.call_llm`

过滤器的 `return` 之前都设了 `event.call_llm = True`。这个赋值容易被理解反：

```python
# platform/astr_message_event.py:144
self.call_llm = False        # 默认值

# pipeline/process_stage/stage.py:66-73
if (
    not event._has_send_oper
    and event.is_at_or_wake_command
    and not event.call_llm
):
    async for _ in self.agent_sub_stage.process(event):   # 兜底跑主 LLM
```

`call_llm = True` 的语义是**阻止框架兜底**，不是"允许调用"。而且兜底只对 `@`/唤醒词消息生效——**一张 @ 了 bot 的卡片，如果插件 return 时没设这一行，框架会在后面补跑一次主 AI 并回复它**。

实测确认：卡片被丢弃后 12 秒内，LLM 调用 0 次、发送 0 次。

## 4.2 哨兵：位置比逻辑更重要

### 为什么不能靠"清洗成空"

回复链路上有一段：

```python
_cleaned_reply = MessageCleaner.clean_message(reply_text)
if _cleaned_reply and _cleaned_reply != reply_text:
    reply_text = _cleaned_reply
```

`if _cleaned_reply` 是**真值判断**：清洗结果为空时，条件为假，`reply_text` 保留原文照发。而且 `clean_message` 根本不认识哨兵。

所以"让清洗把回复洗成空、以此达成不发送"这条路从根上不通，必须在它**之前**独立判定。

### 插入点选在 poke 剥离之前

`on_decorating_result` 里依次是：空文本检查 → poke 标记剥离 → 内容清洗 → 写 `raw_reply_cache` → 写 `_pending_bot_replies` → 输出过滤 → 重复检测。

哨兵插在**第一步之后、poke 剥离之前**。这个位置的好处是：`raw_reply_cache`、`_pending_bot_replies`、`_poke_on_demand_targets`、`recent_replies_cache` 全都还没写入，拦截后不需要回滚任何状态。

```python
if "[[NO_REPLY]]" in reply_text:
    _noreply_text = reply_text.replace("[[NO_REPLY]]", "").strip()
    if _noreply_text.strip(" \t\r\n\u3000。，、；：！？…—·,.!?;:~～\"'…"):
        # 剥完还有正文：净化 chain 后照常发送，避免标记外泄
        ...
    else:
        logger.info("🛑 [main_no_reply] 主AI判定本条不值得回复，已拦截发送")
        event.clear_result()
        event.call_llm = True
        self._agent_done_flags.discard(message_id)
        return
```

`_agent_done_flags` 那行是必须的：它在 `on_llm_response` 阶段已写入，正常清理点在 `after_message_sent` 里，而 `clear_result()` 之后那个回调不会触发。

## 4.3 提示词：给模型一个唯一的机器出口

`SYSTEM_REPLY_PROMPT` 里有**三处**禁止判断的表述，不是两处：

| 位置 | 原文 |
| --- | --- |
| 任务说明 | 你无需考虑"该不该回复"或"该不该开口"——这些判断已经完成 |
| 核心原则 1 | 你只负责生成回复文本，不负责判断、不负责分析 |
| 回复身份 | 这是"说什么"的生成步骤，不是"要不要回复"的判断步骤 |

只改其中两句会互相打架，三处要一起动。但**只把"不许判断"改成"可以判断"是个陷阱**：没有唯一的机器出口，模型会输出解释性拒答——"我觉得这句不用回"、"这个不关我事"，正好撞上旁边那条"不要输出'是否该回复''现在该不该开口'之类的内部判断"。

所以标记规则必须写成硬约束：

> 决定不回复时，整条回复只能输出 `[[NO_REPLY]]`，不得输出任何其它文字、解释、理由或标点。

第一版示例里写了"旁人之间的闲谈"作为不值得回复的例子，评审时被砍掉了。理由很实在：它描述的是**消息的参与者**，不是**消息有没有互动价值**。下面这段对话里 A 和 B 在互相交谈，但希可完全有位置参与：

> 用户 A：「希可昨天说的那个事情，你们怎么看？」
> 用户 B：「我觉得挺有意思的。」
> 用户 A：「对吧，我也这么觉得。」

替换后的措辞明确禁止把"没 @ 我"当成拒答理由：

```text
如果你看过之后确认这条消息确实不值得响应（例如纯表情、无实质内容的重复刷屏，
或当前话题与你无关且确实没有自然接话点），就按【特殊标记】里的 [[NO_REPLY]] 规则处理。
不要仅仅因为消息没有直接 @ 你、其他用户正在互相交谈，就决定不回复。
只要消息与你有关、延续了你参与的话题，或存在自然的互动机会，就可以正常参与。
```

## 4.4 直连分流：只做两条，含图不碰

原本规划的三态（明确要回 / 明确不要 / 模糊走 LLM）在实施时收缩成两态半：

| 规则 | 判据 | 24h 收益 |
| --- | --- | --- |
| 关键词命中 → 直连 | `has_trigger_keyword` | −54 次决策调用（−16.8%） |
| 引用回复 bot → 直连 | `Reply.sender_id == 机器人自身 QQ` | 未知 |
| 模糊 → 仍走决策 AI | 其余全部 | — |

"明确不要"那一档**没有做**。原因是规则判据本身的上限：进入这个分支时 @ 一定为假，剩下可用的硬信号只有关键词、引用、疑问句、纯表情，这些只能支撑"明确相关"。「明确无关」的候选判据——"最近 N 条 bot 没参与 + 没提到希可 + 不是回复"——恰好会误杀设计里最在意的那类消息：两个人在聊希可但没点名。

引用回复的判定有一个意外的好消息。`Reply` 组件的 `sender_id` 本来以为是空的，因为日志里的原始事件只有 `{'id': ...}`。查了适配器才发现它会主动查一次被引用消息再补全：

```python
# aiocqhttp_platform_adapter.py:303-339
reply_seg = Reply(
    id=abm_reply.message_id,
    sender_id=abm_reply.sender.user_id,   # ← 被引用消息的发送者
    ...
)
```

所以判定只需要一句话，不需要额外维护引用关系、也不需要新增 API 调用（那次 `get_msg` 是收消息时早就发过的）。

## 5.2 D 档：哨兵一次都没被用过

部署后 2 小时 26 分的真实数据：

| 指标 | 数值 |
| --- | --- |
| 群消息 | 561 |
| 决策 AI 调用 | 462（**82.4%**） |
| 判 yes / no | 157 / 305 |
| 实际发送 | 184 |
| **`main_no_reply`** | **0** |

提示词确认已生效（运行时读出的常量长度 4,081 字符、`NO_REPLY` 存在、旧句"你无需考虑"已消失），补丁在跑，但**模型从没输出过哨兵**。

抽一段密集对话看（三分钟内）：

```
22:53:16 希可 → Yvonne      22:53:23 希可 → 鱼鱼
22:53:32 希可 → Yvonne      22:53:39 希可 → 鱼鱼
```

人类发约 20 条，希可发 11 条，回复率约 55%。**几乎每条都接了一句。**

原因不难理解：在五六个人你来我往的对话里，"这条消息有没有互动价值"这个判据几乎恒为真——每一条确实都有接话点。哨兵适合的是"一大段闲聊里偶尔插一句"，不是"多人轮转"。

## 5.3 一个让统计失真的发现

我一开始把 `Prepare to send` 的次数直接当成"回复了几条"，于是算出回复率 31%、并得出"话痨"的结论。后来发现这个数错了。

发送 184 次，而决策 yes 只有 157 次，多出 27 条。用时间对齐（每条发送找 90 秒内最近的决策 yes）跑出来：

```
发送总数 184
决策yes总数 157
能对齐上 yes 的发送 148
对不上的发送 36
```

那 36 条对不上的，内容长这样：

```
21:58:36  找了半天没找着，希可这边搜不出来。要不你把链接发过来
21:59:04  原来是这个乐队，名字长得一口气念不完。希可拿这个再搜搜看
22:00:59  歌是找着了，可希可这边放不出声
22:02:01  一直顶着不松，听完还嗡嗡响——这种歌是上头的
```

**这是 agent 工具调用的产物**。一次决策 yes 之后，主 AI 做了「搜歌 → 找到名字 → 尝试播放 → 播不出来」这一串工具调用，每一轮都输出一段文字并各自发出，于是产生多次发送。

结论：`Prepare to send` 的次数**不等于**「回复了几条消息」。一次决策可以产生 1～N 次发送。凡是拿它做分母算"回复率"的统计，都会失真。

## 5.4 C 档没有部署

C 档补丁（两条直连）已经写好并通过验证，但**没有上线**。原因是顺序问题：直连会让一部分消息跳过决策 AI 直接进主 AI，如果哨兵的自主拒答还不可靠，这些消息就会变成强制发言。

按 24 小时数据，关键词命中的 54 条如果全部直连，就是每天多 54 次必须开口。所以顺序必须是**先哨兵、后直连**，且哨兵稳定运行一段之后再放开。

# 六、复盘

## 6.1 三条经验

**第一，先核对"必经关卡"这个前提，再谈优化。**

设计里最核心的一句是"决策 AI 从每条消息的必经关卡变成辅助组件"。但数据显示它本来就在概率门之后，只处理 63.6% 的消息。按错误的前提去改，会做出一个"优化"但指标不动的东西。

**第二，关掉一个 LLM 判定不等于省钱。**

那 221 次判 `no` 的调用如果全部交给主 AI，token 消耗是**上升**的——把一次约 732 个计费 token 的轻判定，换成一次完整人格对话生成。省下来的只有免费额度的消耗速度和延迟，不是成本。

真正该找的是"被召起来却必然得出同一个结论"的调用：命中触发关键词还要问"要不要回"、下发展示成卡片还要问"这条能不能回"。这一类才是纯浪费。

**第三，"可以不说话"的能力，不等于"少说话"的效果。**

哨兵上线后零触发是最有价值的一条数据。它说明：当每条消息确实都有互动价值时，模型不会用拒绝权。如果目标是让 bot 在密集对话里少插话，需要的是**发言频率约束**（冷却、疲劳、密度），而不是**单条价值判断**。这是两个不同的机制，用错方向会得出"改了但没效果"的结论。

## 6.2 一处值得记住的细节

排查期间有一个反复出现的坑：**日志行号不能直接对源码**。

插件的源码经历过多次局部改写，`docker logs` 里的 `main:6589` 在历史版本里对应 +72 偏移、`main:6648` 对应 +13、`main:6661` 才是 0。混着看会以为"两版内容差异很大"，实际只是版本迁移的残留。

正确的做法是：先确认容器实际运行的文件（比对 md5 与 `__pycache__` 里 pyc 头部的 mtime/size），再做日志行号与磁盘行号的对齐抽样。本次确认了 353 个不同行号零偏移，后面所有补丁才能精确落点。
