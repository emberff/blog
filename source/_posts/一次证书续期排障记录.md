起因只是一句"服务器上的自签证书过期了，怎么续期？"，结果越查越大：**11 张 Let's Encrypt 证书其实全都过期了**，续期途中又撞上通配符证书的手动验证、权威 DNS 不在你以为的那家云、自定义 Nginx 的 PID 文件对不上、以及一个被 Markdown 代码围栏污染的续期脚本。本文按 **起因 → 定位 → 解决 → 验证** 的顺序把整个过程复盘一遍，最后给出一套可以直接用的自动续期方案。
{% endnote %}

# 一、背景与初始问题

先把环境交代清楚，本次所有坑几乎都和这套"非标准"环境有关：

| 项目 | 值 |
| --- | --- |
| 系统 | CentOS 8.5 (2111) |
| Python | 3.6.8 |
| pip | 9.0.3 |
| Certbot | 1.22.0（`/usr/bin/certbot`，pip 安装） |
| Nginx | 自定义编译版 `/usr/local/nginx/sbin/nginx` |
| 域名 | `hopai.cn` 及其一批子域名 |

最开始的问题是：**用 OpenSSL 自己生成的自签名证书过期了，怎么"续期"？**

这里必须先把概念掰正：

{% note info %}
**自签名证书没有"续期"这个说法。** 它不像 Let's Encrypt 那样有 ACME 协议可以复用原有 lineage 重新签发，所谓"续期"本质上就是**重新生成一张新的自签名证书**。
{% endnote %}

OpenSSL 的 `req -x509` 可以直接生成自签名证书，用 `-days` 指定有效期。

## 1.1 分情况重新生成自签名证书

**情况 A：原私钥还在（推荐，可继续沿用原私钥）**

```bash
openssl req -x509 \
  -key /etc/nginx/ssl/server.key \
  -out /etc/nginx/ssl/server.crt \
  -days 3650 \
  -subj "/CN=example.com"
```

**情况 B：连原私钥也没了，直接连私钥一起重新生成**

```bash
openssl req -x509 \
  -newkey rsa:2048 \
  -keyout /etc/nginx/ssl/server.key \
  -out /etc/nginx/ssl/server.crt \
  -days 3650 \
  -nodes \
  -subj "/CN=example.com"

chmod 600 /etc/nginx/ssl/server.key
```

## 1.2 一个容易被忽略的关键点：subjectAltName

如果证书要支持多个域名，**只有 `CN` 是不够的**。现代浏览器（Chrome 58+ 起）早已不再回退到 `CN` 匹配，必须带上 `subjectAltName`，否则浏览器照样判定"证书与域名不匹配"。

```bash
openssl req -x509 \
  -key /etc/nginx/ssl/server.key \
  -out /etc/nginx/ssl/server.crt \
  -days 3650 \
  -subj "/CN=example.com" \
  -addext "subjectAltName=DNS:example.com,DNS:www.example.com"
```

## 1.3 自签名证书的查看与生效

查看有效期与主体：

```bash
openssl x509 -in /etc/nginx/ssl/server.crt -noout -dates
openssl x509 -in /etc/nginx/ssl/server.crt -noout -text   # 完整信息
```

重点看 `notBefore=` 和 `notAfter=`。

改完证书后**不需要停服务**，只要 reload：

```bash
/usr/local/nginx/sbin/nginx -t        # 先测配置
/usr/local/nginx/sbin/nginx -s reload # 再平滑重载
```

{% note warning %}
判断"这张证书到底属于谁"，最省事的就是查 `Issuer`：自签名证书的 `Issuer` 和 `Subject` 完全一样，而 Let's Encrypt 签发的一定带 `Let's Encrypt` 字样。
{% endnote %}

```bash
openssl x509 -in <证书路径> -noout -issuer -subject -dates
```

# 二、转折：这根本不是自签证书

按上面的思路去查线上证书，结果发现 `Issuer` 是 Let's Encrypt——**问题性质完全变了**。

先看证书状态：

```bash
openssl x509 -in /etc/letsencrypt/live/api.hopai.cn/fullchain.pem \
  -noout -dates -issuer -subject
```

或者直接问 Certbot：

```bash
certbot certificates
```

结果比预想的严重得多：**Certbot 管理的 11 张证书全部已经过期**，而不是某一两张。

```
api.hopai.cn   : 2026-07-06 过期 (INVALID: EXPIRED)
fushi.hopai.cn : 2026-09-05 过期
hopai.cn       : 2025-12-20 过期
nest.hopai.cn  : 2026-08-25 过期
...
```

而当时已经是 2026-09-24，也就是说这批证书**全部躺在过期状态里好几个月了**。

{% note info %}
好消息是：**不需要删除任何证书，也不需要重建 Certbot 配置。** `certbot renew` 会复用原证书的验证方式和 renewal 配置，必要时用 `--cert-name` 只续其中一张。
{% endnote %}

# 三、全量续期：先看配置，别急着重签

## 3.1 明确"不要做"的事

- ❌ **不要** `rm -rf /etc/letsencrypt/...`：这会把证书续期链（lineage）和配置一起搞乱。
- ❌ **不要**上来就 `certbot certonly` 重建一堆新证书：容易和现有的 11 个 lineage 打架。
- ❌ **不要**一上来就全量 `certbot renew`：先单张验证，确认验证方式可用再批量。

## 3.2 先看 renewal 配置

Certbot 会**记住当初申请证书时用的验证方式**，续期时默认沿用：

```bash
ls -l /etc/letsencrypt/renewal/
cat /etc/letsencrypt/renewal/api.hopai.cn.conf
```

重点看这几个字段：

```ini
authenticator = ...     # standalone / webroot / dns-xxx / manual
installer = ...
pre_hook = ...
post_hook = ...
webroot_path = ...
```

三种常见情况：

| authenticator | 续期时是否需要停 Nginx |
| --- | --- |
| `standalone` | **需要**（Certbot 要自己监听 80 端口） |
| `webroot` | 不需要（验证文件放进网站目录） |
| `dns-xxx` / `manual` | 不需要，走 DNS TXT 验证 |

本例中 `api.hopai.cn.conf` 是：

```ini
authenticator = standalone
```

也就是说续期时 Certbot 需要占用 80 端口，**必须先停掉 Nginx**。而它的配置里并没有 `pre_hook` / `post_hook`，说明之前一直是**手动**停 Nginx 再续期的。

## 3.3 先单张验证，再全量

```bash
# 1. 确认 80 端口是谁占着
ss -ltnp | grep ':80'

# 2. 停掉 Nginx，释放端口
/usr/local/nginx/sbin/nginx -s stop

# 3. 只续这一张（已过期，Certbot 会直接重新签发）
certbot renew --cert-name api.hopai.cn

# 4. 确认新有效期
certbot certificates

# 5. 把 Nginx 拉起来
/usr/local/nginx/sbin/nginx -t && /usr/local/nginx/sbin/nginx
```

`api.hopai.cn` 一次成功，新有效期到 `2026-12-23`，说明 **Certbot + standalone 这条路本身是通的**。于是按同样流程批量执行：

```bash
/usr/local/nginx/sbin/nginx -s stop
certbot renew
/usr/local/nginx/sbin/nginx
```

## 3.4 结果：9 成 2 败

| 证书 | 状态 | 原因 |
| --- | --- | --- |
| api.hopai.cn | ✅ | 已手动续到 2026-12-23 |
| fushi.hopai.cn | ✅ | 续期成功 |
| hopai.cn-0001 | ✅ | 续期成功（仅 `hopai.cn`） |
| **hopai.cn** | ❌ | manual 验证方式缺少 manual-auth-hook |
| kateadmin.hopai.cn | ✅ | 续期成功 |
| **katenest.hopai.cn** | ❌ | webroot 验证返回 404 |
| lumi.hopai.cn | ✅ | 续期成功 |
| manage.hopai.cn | ✅ | 续期成功 |
| mvp.hopai.cn | ✅ | 续期成功 |
| nest.hopai.cn | ✅ | 续期成功 |
| resume.hopai.cn | ✅ | 续期成功 |

11 张里 9 张恢复，剩下 2 张是**历史遗留的配置问题**，跟这次操作无关，需要单独处理。

# 四、两张"续不掉"的证书

## 4.1 hopai.cn + \*.hopai.cn：manual + DNS-01

报错：

```
The manual plugin is not working
An authentication script must be provided with --manual-auth-hook
when using the manual plugin non-interactively.
```

看配置就明白了：

```ini
pref_challs = dns-01,
authenticator = manual
```

两个关键点：

1. **通配符证书 `*.hopai.cn` 不能用 HTTP-01 验证，只能用 DNS-01**（Let's Encrypt 从 2018 年起支持通配符，但强制走 DNS-01）。
2. `manual` 插件在**非交互式**场景下必须提供 `--manual-auth-hook`，否则 Certbot 根本不知道该怎么替你添加 TXT 记录 —— 这就是 `certbot renew` 必然失败的原因。

手动续期（需要自己到 DNS 服务商加 TXT 记录）：

```bash
certbot certonly \
  --manual \
  --preferred-challenges dns \
  --cert-name hopai.cn \
  -d hopai.cn \
  -d "*.hopai.cn"
```

Certbot 会提示你在 `_acme-challenge.hopai.cn` 下添加一条 TXT 记录，加完用 `dig` 确认生效再回车：

```bash
dig TXT _acme-challenge.hopai.cn +short
```

{% note warning %}
**注意区分两张同名但不同的证书，一张都不能删。** 名为 `hopai.cn` 的这张包含 `hopai.cn` + `*.hopai.cn`（❌ 未续期），而名为 `hopai.cn-0001` 的只包含 `hopai.cn`（✅ 已续期）。它们很可能对应不同的 Nginx 配置，贸然删除任何一张都可能让某个站点掉证书。
{% endnote %}

## 4.2 katenest.hopai.cn：webroot 404

报错非常明确：

```
Type: unauthorized
Invalid response from
https://katenest.hopai.cn/.well-known/acme-challenge/xxxxx: 404
```

这说明不是 DNS 问题，而是：

> **Certbot 写入的 webroot 目录 ≠ Nginx 实际提供 `/.well-known/acme-challenge/` 的目录。**

排查方法：

```bash
cat /etc/letsencrypt/renewal/katenest.hopai.cn.conf
```

对比里面的 `webroot_path` 与 Nginx 配置中 `location /.well-known/acme-challenge/` 的 `root` 是否指向同一个目录，一致即可。

# 五、想让通配符自动续期：踩了"权威 DNS 不在阿里云"的坑

既然 `manual` 每 90 天都要人工加 TXT，长期方案自然是**换成 DNS API 插件自动续期**。

## 5.1 版本兼容是第一道坎

Certbot 1.22.0 + Python 3.6.8 这个组合比较老，**不能直接装最新插件**（新版 `certbot-dns-aliyun` 要求 `certbot>=2.0.0`）。旧版 `0.38.1` 明确支持 Python 3.6：

```bash
pip3 install 'certbot-dns-aliyun==0.38.1'
certbot plugins        # 确认能看到 dns-aliyun
```

凭据文件单独存放，权限必须收紧：

```bash
mkdir -p /root/.secrets/certbot && chmod 700 /root/.secrets/certbot
vi /root/.secrets/certbot/aliyun.ini
chmod 600 /root/.secrets/certbot/aliyun.ini
```

```ini
dns_aliyun_access_key = 你的AccessKeyID
dns_aliyun_access_key_secret = 你的AccessKeySecret
```

## 5.2 dry-run 报错，顺藤摸瓜找到了真正的坑

```bash
certbot certonly \
  --authenticator dns-aliyun \
  --dns-aliyun-credentials /root/.secrets/certbot/aliyun.ini \
  --cert-name hopai.cn \
  -d hopai.cn -d "*.hopai.cn" \
  --dry-run
```

输出里有两个问题：

```
Unsafe permissions on credentials configuration file: /root/.secrets/certbot/aliyun.ini
...
Incorrect TXT record "b3YMfZUG..." found at _acme-challenge.hopai.cn
```

第一个好办（`chmod 600` + `chown root:root`）。第二个才是关键 —— 插件明明调用阿里云 API 成功创建了 TXT 记录，为什么 Let's Encrypt 还查不到正确的值？

**因为你要查"谁是权威 DNS"，而不是"DNS 记录加在哪家云控制台"。**

```bash
dig TXT _acme-challenge.hopai.cn +short
dig NS hopai.cn +short
```

结果：

```
elliot.ns.cloudflare.com.
emely.ns.cloudflare.com.
```

{% note warning %}
**`hopai.cn` 的权威 DNS 是 Cloudflare，不是阿里云。**

所以 `dns-aliyun` 插件虽然成功调用了阿里云 API 写入了 TXT 记录，但那**不是公网权威记录**。Let's Encrypt 最终查询的是 Cloudflare 上的 `_acme-challenge.hopai.cn`，自然只能看到一个"旧的、不匹配的" TXT 值，于是报 `Incorrect TXT record`。

正确的组合应该是 `certbot-dns-cloudflare` + Cloudflare API Token（Token 权限限制到具体 Zone 的 `DNS:Edit`），凭据存到 `/root/.secrets/certbot/cloudflare.ini`。
{% endnote %}

**这次踩坑的经验：DNS-01 验证失败时，第一件事永远是 `dig NS <域名>` 确认权威 DNS 到底是哪家，不要想当然以为 DNS 托管在你配 API 的那家云。**

好在这次绕的弯路没有副作用：阿里云的 RAM 用户和 AccessKey 只是"对这张证书没用"，本身不产生任何影响，先留着即可。

# 六、搭建自动续期：独立脚本 + /etc/cron.d

## 6.1 先把旧任务找出来

用户提到"以前写过自动续期脚本，但可能没设置 Nginx 启停所以失败"。与其重写，不如先找旧的：

```bash
crontab -l
cat /etc/crontab
grep -RniE 'certbot|letsencrypt|acme' /etc/cron* 2>/dev/null
find /etc/letsencrypt/renewal-hooks -type f -ls 2>/dev/null
grep -H "authenticator" /etc/letsencrypt/renewal/*.conf
```

结论：`crontab -l` 里只剩一条日志清理任务，`/etc/crontab`、`/etc/cron.d/`、`renewal-hooks` 里**都没有任何 Certbot 相关配置**——旧的自动续期确实已经消失了（这正好解释了证书为什么会集体过期）。

## 6.2 方案设计要点

1. **standalone 证书续期时必须释放 80 端口** → 必须先停 Nginx，续完再拉起；
2. Nginx 不是 systemd 管理的，**不能用 `systemctl stop nginx`**；
3. 不管 Certbot 成功还是失败，**都必须把 Nginx 恢复起来**（用 `trap`）；
4. 加**文件锁**，避免定时任务重入；
5. 启动前先 `nginx -t` 校验配置，避免配置错误导致 Nginx 起不来；
6. 输出全部写日志，方便事后排查。

## 6.3 续期脚本

创建 `/usr/local/sbin/certbot-renew.sh`：

```bash
#!/bin/bash
# ============================================================
# Let's Encrypt auto renewal script
# Nginx: /usr/local/nginx
# ============================================================
set -u

CERTBOT="/usr/bin/certbot"
NGINX="/usr/local/nginx/sbin/nginx"
NGINX_CONF="/usr/local/nginx/conf/nginx.conf"
NGINX_PID_FILE="/usr/local/nginx/logs/nginx.pid"
LOG="/var/log/certbot-renew.log"
LOCK="/var/run/certbot-renew.lock"

exec >> "$LOG" 2>&1
echo
echo "=================================================="
echo "[$(date '+%Y-%m-%d %H:%M:%S')] Certbot renewal started"

# ---------- 防止重复执行 ----------
exec 9>"$LOCK"
if ! flock -n 9; then
    echo "Another renewal process is running. Exit."
    exit 0
fi

# ---------- 程序检查 ----------
for f in "$CERTBOT" "$NGINX"; do
    [ -x "$f" ] || { echo "ERROR: not found or not executable: $f"; exit 1; }
done
[ -f "$NGINX_CONF" ] || { echo "ERROR: config not found: $NGINX_CONF"; exit 1; }

# ---------- 通过 PID 文件判断 Nginx 是否在运行 ----------
NGINX_WAS_RUNNING=0
NGINX_PID=""
if [ -f "$NGINX_PID_FILE" ]; then
    NGINX_PID=$(cat "$NGINX_PID_FILE")
    if [[ "$NGINX_PID" =~ ^[0-9]+$ ]] && kill -0 "$NGINX_PID" 2>/dev/null; then
        NGINX_WAS_RUNNING=1
        echo "Nginx master PID: $NGINX_PID"
    fi
fi

# ---------- 停止 Nginx ----------
if [ "$NGINX_WAS_RUNNING" -eq 1 ]; then
    echo "Stopping nginx..."
    "$NGINX" -c "$NGINX_CONF" -s stop
    for i in {1..30}; do
        kill -0 "$NGINX_PID" 2>/dev/null || break
        sleep 1
    done
    if kill -0 "$NGINX_PID" 2>/dev/null; then
        echo "ERROR: nginx failed to stop."
        exit 1
    fi
    echo "Nginx stopped successfully."
fi

# ---------- 无论成败都要恢复 Nginx ----------
cleanup() {
    CERTBOT_EXIT=$?
    echo "Certbot exit code: $CERTBOT_EXIT"
    if [ "$NGINX_WAS_RUNNING" -eq 1 ]; then
        echo "Testing nginx configuration..."
        if ! "$NGINX" -t -c "$NGINX_CONF"; then
            echo "ERROR: nginx configuration test failed."
            exit 1
        fi
        echo "Starting nginx..."
        if ! "$NGINX" -c "$NGINX_CONF"; then
            echo "ERROR: nginx failed to start."
            exit 1
        fi
        sleep 2
        if pgrep -x nginx >/dev/null 2>&1; then
            echo "Nginx started successfully."
        else
            echo "ERROR: nginx process not found after startup."
            exit 1
        fi
    fi
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] Certbot renewal finished."
    exit "$CERTBOT_EXIT"
}
trap cleanup EXIT

# ---------- 执行续期 ----------
echo "Running certbot renew..."
"$CERTBOT" renew --quiet --no-random-sleep-on-renew
exit $?
```

赋权与日志：

```bash
chmod 700 /usr/local/sbin/certbot-renew.sh
chown root:root /usr/local/sbin/certbot-renew.sh

touch /var/log/certbot-renew.log
chmod 600 /var/log/certbot-renew.log
```

## 6.4 定时任务

使用 **系统级 cron 文件**（而不是 `crontab -e`），这样更不容易被用户级操作误删：

```bash
cat > /etc/cron.d/certbot-renew <<'EOF'
17 3 * * * root /usr/local/sbin/certbot-renew.sh
EOF

chmod 644 /etc/cron.d/certbot-renew
chown root:root /etc/cron.d/certbot-renew
```

{% note info %}
**为什么可以"每天"执行？** 因为 `certbot renew` 自己会判断每张证书是否已经进入续期窗口（默认到期前 30 天），没到期的直接跳过。所以"每天执行"并不等于"每天重新申请"。
{% endnote %}

# 七、排障实录：脚本为什么跑不起来

脚本写完了，但真正跑起来又是一路踩坑，这一节反而是最有价值的部分。

## 7.1 坑一：`nginx -s stop` 报 PID 文件不存在

日志里出现：

```
[error] open() "/usr/local/nginx/logs/nginx.pid" failed (2: No such file or directory)
ERROR: nginx failed to stop.
```

但从 `pgrep nginx` 看，Nginx 明明活得好好的。这就很矛盾：**进程在，PID 文件却不在。**

排查：

```bash
ps -ef | grep '[n]ginx'
readlink -f /proc/$(pgrep -o nginx)/exe
```

结果真相大白：

```
root 466551 1 ... nginx: master process nginx -c /etc/nginx/nginx.conf
```

**实际运行的 Nginx 是用 `/etc/nginx/nginx.conf` 启动的**，而不是我们脚本假定的 `/usr/local/nginx/conf/nginx.conf`！

这就解释了一切：

- `nginx -s stop` 按 `/usr/local/nginx/conf/nginx.conf` 去找 PID 文件 → 找不到 → 报错；
- 日志里那些 `/etc/nginx/conf.d/katenest.hopai.cn.conf` 之类的 warning 也顺理成章了。

{% note info %}
**顺带澄清一个概念：进程 PID 和 PID 文件是两回事。** 进程 PID 每次启动都由内核分配，**每次都会变**；而 PID 文件路径是固定的（如 `/usr/local/nginx/logs/nginx.pid`），文件里记录"**当前这次** master 进程的 PID"。所以脚本里**绝不能写死某个 PID**，而应该每次去读 PID 文件。
{% endnote %}

**解决：让 `/usr/local` 这套 Nginx 接管。** 关键是**先测试再动手**，避免中途服务不可用：

```bash
# 1. 先测试 /usr/local 这套配置能不能起来
/usr/local/nginx/sbin/nginx -t -c /usr/local/nginx/conf/nginx.conf

# 2. 停掉旧的（用明确的 master PID，不要 pkill nginx）
kill -TERM 466551
ps -ef | grep '[n]ginx'

# 3. 启动 /usr/local 版
/usr/local/nginx/sbin/nginx -c /usr/local/nginx/conf/nginx.conf

# 4. 确认这次真的是它
readlink -f /proc/$(pgrep -o nginx)/exe
ls -l /usr/local/nginx/logs/nginx.pid
```

这次 PID 文件正常生成，之前那个 `open() ... nginx.pid failed` 的问题随之解决。

## 7.2 坑二：脚本执行了，日志却一行没加

更诡异的现象来了：手动执行 `/usr/local/sbin/certbot-renew.sh`，终端立刻返回，但日志文件**没有任何新增**。而脚本第一件事就是 `echo "[$(date ...)] Certbot renewal started"`，只要执行了就一定有输出。

排查：

```bash
file /usr/local/sbin/certbot-renew.sh
xxd -l 32 /usr/local/sbin/certbot-renew.sh
```

结果：

```
00000000: 6060 6062 6173 680a
```

`6060` 是反引号，`6062 6173 68` 是 `bash`——**脚本文件的第一行竟然是 Markdown 的代码围栏 ` ```bash `！**

复制代码块的时候，把 Markdown 的围栏一起复制进文件了。这会导致：

- `file` 把它误判成 `Dyalog APL transfer`；
- `bash -n` 居然**不报错**，因为 ` ```bash ` 被当成了一段普通语句/命令处理，所以"语法检查通过"并不能证明文件内容正确。

修复（删掉首尾的围栏行）：

```bash
sed -i '1{/^```bash$/d;}' /usr/local/sbin/certbot-renew.sh
sed -i '${/^```$/d;}'     /usr/local/sbin/certbot-renew.sh

# 验证：应该以 2321 2f62 696e 2f62 6173 680a 开头，也就是 #!/bin/bash
xxd -l 16 /usr/local/sbin/certbot-renew.sh
head -5 /usr/local/sbin/certbot-renew.sh | cat -A
```

修完再跑，日志终于正常：

```
Nginx master PID: 568751
Stopping custom nginx...
Nginx stopped successfully.
Running certbot renew...
Certbot finished with exit code: 0
Testing nginx configuration...
syntax is ok
test is successful
Starting custom nginx...
Nginx started successfully.
```

{% note warning %}
**血的教训：** Linux 脚本尽量用**纯 ASCII**、不带中文注释，并且**永远不要把 Markdown 代码块整体复制粘贴**进服务器文件。如果非要多行，用 `cat > file <<'EOF' ... EOF` 或直接在服务器上写。
{% endnote %}

# 八、验证定时任务是否真的会执行

用户提出要写个测试脚本：查看证书过期时间 → 把 cron 改到 5 分钟后 → 再查 → 恢复原时间。

这里有个**认知很重要**：

{% note info %}
`certbot renew` **只有在证书进入续期窗口时才会真正更新证书**。所以"5 分钟后证书过期时间没变"是**正常现象**，不能据此判断定时任务失败。

判断定时任务是否生效的正确标准是：**`/var/log/certbot-renew.log` 里有没有出现新的执行记录**。
{% endnote %}

于是测试脚本 `/usr/local/sbin/test-certbot-cron.sh` 的核心逻辑是：

1. 备份原 cron 文件；
2. 把执行时间临时改成"5 分钟后"；
3. 等到目标时间并等待 cron 触发；
4. 用 `awk` 找出**时间戳晚于测试开始时刻**的 `Certbot renewal started` 记录（避免把上一次的日志误判为本次）；
5. 检查是否有 `Certbot renewal finished.`；
6. 恢复原 cron 并输出明确的 `RESULT: CRON TEST PASSED / FAILED`。

# 九、踩坑清单汇总

| # | 现象 | 根因 | 解决 |
| --- | --- | --- | --- |
| 1 | 自签名证书"续期" | 概念错误，自签名无续期一说 | 用 `openssl req -x509` 重新生成，并带 `-addext subjectAltName` |
| 2 | 11 张证书全部过期 | 旧的自动续期任务已消失 | 先手动 `certbot renew` 恢复，再重建自动续期 |
| 3 | 部分证书续期失败 | `authenticator` 方式不同（standalone 需停 Nginx） | 先看 renewal 配置，再决定是否停服务 |
| 4 | `hopai.cn` 通配符续不掉 | `manual` + DNS-01 缺少 `manual-auth-hook` | 手动加 TXT 续期，长期改用 DNS API 插件 |
| 5 | `katenest.hopai.cn` 404 | webroot 目录与 Nginx 实际目录不一致 | 对齐 `webroot_path` 与 `location` |
| 6 | DNS-01 报 `Incorrect TXT record` | 权威 DNS 在 **Cloudflare**，插件写到了阿里云 | `dig NS` 确认权威 DNS，换对应的插件 |
| 7 | `nginx -s stop` 报找不到 PID 文件 | 实际运行的 Nginx 用的是 `/etc/nginx/nginx.conf` | 明确 Nginx 启动方式与 PID 文件位置 |
| 8 | 脚本执行了却不写日志 | 文件首行混进了 Markdown 代码围栏 `` ```bash `` | `sed` 删除首尾围栏，用 `xxd` 确认文件头 |

除了技术问题，这次还踩了一堆**命令行使用上的低级坑**，但都很真实，一并记下：

- **反斜杠后面多了个空格**：`\ ` 不是续行符，导致整条被拆成多个参数，Certbot 直接打印 usage。要用 `\⏎`，不是 `\   ⏎`。
- **heredoc 的 `EOF` 和内容写在同一行**：卡在 `heredoc>` 提示符里，`EOF` 必须独占一行。
- **把示例输出当命令粘贴**：比如把 `-rw-r--r-- 1 root root ...` 这行提示当成命令执行，得到 `command not found`。
- **多条命令写一行**：`which certbot certbot --version ...` 会被 `which` 当成多个要查找的命令名；`bash -n script echo $?` 里 `echo $?` 会被当成参数。
