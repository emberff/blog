### 6.1 `.idea/` 噪声：加 `.gitignore` 或 `.gitattributes`（推荐先做）

现状：`.idea/*` 在 WSL 侧反复显示 modified，每次提交都要 `git checkout -- .idea`（第 3.12 条）。两种最小做法：

- `.gitignore` 追加 `.idea/`（如果确定不共享 IDE 配置）——最省事；
- 或保留跟踪但加 `.gitattributes` 统一行尾，消除 CRLF/LF 判定差异：
  ```
  * text=auto eol=lf
  *.png binary
  *.jpg binary
  *.webp binary
  ```

### 6.2 多份工作副本：动手前先拉取（2026-09-30 改为此策略）

**背景**：本机可能同时存在多份克隆（`/home/emberff/blog`、`C:\Users\15222\blog`）。历史上出现过"GitHub 侧已更新、某份本地副本 HEAD 还停在旧提交、新文章一直是未跟踪文件"的漂移，当时的对策是"只以 WSL 侧为准、另一侧只读"。

**现在的策略**：不区分主副，**动手前先拉取**：

```bash
cd <你正在用的那份副本>
git pull --ff-only origin main
git log -1 --oneline      # 确认 HEAD 与 origin/main 是同一个 sha
```

**为什么改**：把"哪一侧是主体"写进手册，会让人以为另一侧不能用；而真正要防的只有一件事——**基于旧版本改动**。一条 `git pull` 就解决了，不需要维护主副关系。

**仍然成立的两条技术事实**（与主副无关）：

- 从 WSL 访问 `/mnt/c` 构建会 `EACCES`、`hexo s` 会卡死（第 3.1 / 3.8 条）——9p 挂载的限制；Windows 原生侧不受影响。
- `node_modules` 不随 `git pull` 更新，`package.json` 变化后要重跑 `npm install`（缺 `hexo-all-minifier` 时首页压缩失效：36913 B vs 25877 B）。

**状态**：✅ 已定为本仓库策略（2026-09-30）。

### 6.3 「清理 + 构建 + 部署」已固化为 `npm run publish`（2026-09-27 已完成）

**以后部署用这一条**：


### 6.4 给部署加前置检查

部署前至少确认三件事（**目前靠自觉，尚未脚本化**）：

1. `git status --porcelain` 干净（没有未提交的文章改动被漏掉）；
2. 本地 HEAD == `origin/main`（源码已 push，没出现"部署了新文章但源码仓库还是旧的"）；
3. `git config --global user.name` / `user.email` 非空（防第 3.2 条的静默失败）。

现成的一条命令：

```bash
cd /home/emberff/blog
git status --porcelain && git rev-parse HEAD origin/main && git config --global user.name && git config --global user.email
```

> 注意一个顺序陷阱：**改了 `package.json`（比如刚加 `publish`）会让自己处于"未提交"状态**，与第 1 条冲突。正确顺序是——先 `git add package.json && git commit && git push`，再 `npm run publish`。因为 `hexo deploy` 推的是 `public/` 产物、不是源码工作区，源码脏不影响部署本身；但"部署的版本 == 源码的版本"这个可追溯性要求它是干净的。

### 6.13 body 内脚本改 defer：消除 0.54s 串行链（2026-10-02 已完成）

**做了什么**：新增 [`scripts/defer-scripts.js`](../scripts/defer-scripts.js)（Hexo `after_render:html` 过滤器，优先级 5，早于 hexo-all-minifier 的默认 10），在构建期做两件事：

1. 给 **body 里的 11 个外链脚本**加 `defer`；
2. 把夹在中间、依赖这些脚本的 **2 个内联脚本**包进 `DOMContentLoaded`。

**为什么**：fluid 主题把脚本裸放在 body 末尾（无 `defer`/`async`），浏览器只能「下载一个 → 执行一个 → 再请求下一个」。实测这 11 个脚本串行占 **0.54s**，其中 jQuery 一个就 87.7 KB、`bootstrap.min.js` 61 KB。

**为什么内联脚本也得动**：内联脚本不受 `defer` 影响、解析到就执行，会制造错序——
- `NProgress.configure(...)` 依赖 `nprogress.min.js`
- `Fluid.plugins.typing(...)` 依赖 `plugins.js` + `typed.js`

不推迟它们就会在依赖之前执行而报 `undefined`。规范保证 defer 脚本先于 `DOMContentLoaded` 回调执行，所以包一层就恢复了顺序。

**刻意没做的两件事**（做了会退化，别"优化"回来）：

- **head 里的 `utils.js` / `color-schema.js` 保持同步**：`color-schema.js` 必须在首次绘制前写 `data-user-color-scheme`，defer 会闪白屏；而它依赖 `Fluid.utils`（由 `utils.js` 提供），所以两个都不能 defer。代价是这两个各占一次串行请求（顺畅 0.06s，抖动时各 0.33s）。
- **不换 CDN 源**：实测 baomitu / npmmirror / elemecdn 下载 jQuery 都是 0.088–0.118s，差异 **< 0.03s**；jsdelivr 0.13–0.31s 反而更慢。该段配置在 `_config.fluid.yml:1152` 的 **`static_prefix:`**（⚠️ **段名不是 `cdn:`**，2026-10-02 调研时确认；本站配置里根本没有 `cdn:` 键），可以随便改但没有收益——所以别为了"换源"折腾。
  顺带澄清：那 20 个 `lib.baomitu.com` 前缀**是主题自带的默认值**，不是本站自定义；本站真正覆盖的只有 3 处 —— `waline`（走 npmmirror）、`mermaid`（10.4.0，主题默认 8.14.0）、`busuanzi`。所以"换源"实际只影响这 3 个。

### 6.16 slogan 的 emoji 打字时闪出白色菱形问号（2026-10-02 已完成）

**现象**：首页 slogan 打字过程中，🍃 和 🌕 的位置会闪出**白色菱形中间一个问号**（即 `�`，U+FFFD 的替代字形）。

**根因**：**不是编码问题**——源文件、构建产物、线上 HTTP 头都是合法 UTF-8（已逐项验证）。真正的原因是打字机：

- typed.js 按 **UTF-16 码元**逐字推进（源码里用 `substr`，逐 1 个 code unit）；
- emoji 是**代理对**，占 2 个码元：🍃 = `U+1F343` = `D83C DF43`，🌕 = `U+1F315` = `D83C DF15`；
- 于是打字过程中必然出现"只输出了高代理 `\ud83c`"的中间帧，单独一个代理项渲染出来就是 `�`。

**证据**（本地 `hexo server` + 临时同源页面，每 15ms 采样 `#subtitle.textContent`，共 600 次）：

```
采样次数: 600（正常 588 / 异常 12）
首次异常样本 #63 :  textContent = "\ud83c"                    ← 半个叶子
末次异常样本 #257:  ...与山间之明月!\n\n\ud83c                ← 半个月亮
```

**解决**：把 emoji 写成 **HTML 数字实体**，不写裸字符：

```yaml
text: |
  <span class="emoji">&#x1F343;</span>
  ...
  &#x1F315;
```

**为什么这样就对了**：typed.js 的 `htmlParser.typeHtmlChars` 遇到 `&` 会一直跳到 `;`，把**整个实体当作一步**输出——于是浏览器一次性拿到 `&#x1F343;` 并解析成 🍃，不存在"半个字符"的中间帧。它同时被 `backSpaceHtmlChars` 覆盖，所以回删也安全。

**验证**：改后同样采样 **601 次，0 次异常**；打字完成后 `#subtitle` 是真实字符（`'🍃 … 与山间之明月! …🌕_'`，末尾 `_` 是打字光标），页面里既无残留字面实体也无 U+FFFD。布局与错位不受影响（实体渲染出的 emoji 与裸字符同宽）。

**怎么自查**：

```bash

npx hexo clean && npx hexo generate
python3 -c "

h = open('public/index.html', encoding='utf-8').read()

print('裸 emoji:', sum(seg.count(c) for c in '🍃🌕'), '（期望 0）')
print('实体   :', seg.count('&amp;#x'), '（期望 2）')"
```

**通用结论**：**凡是要经过打字机输出的 emoji，都必须写成 HTML 实体**（`&#x1F343;`）。同一类坑对所有"按码元迭代字符串"的 JS 动画都成立。

**⚠️ 关键澄清**：commit 标题写的是「移除 Bootstrap 和 jQuery 依赖」，但**实际只移除了两者的 JS**——v2.0 的 `layout/_partials/css.ejs` 第 1 行仍是 `css_ex(theme.static_prefix.bootstrap, 'css/bootstrap.min.css')`，`_config.yml` 里 `static_prefix.bootstrap` 也仍在。所以省下的是 **约 152 KB**（jquery + bootstrap.min.js），扣掉新增的 hint.css 与 Swup 后**净省约 110~125 KB / 2 个请求**，而不是"省掉 Bootstrap 那 162 KB"。

**新增一个国内访问的负项**：v2.0 把 `fancybox` 与 `swup`(PJAX) 放在 **cdn.jsdelivr.net** 上；实测 jsdelivr 在国内 0.13–0.31s，比 baomitu 的 0.09–0.12s 慢（采样方法见 3.16）。若启用 PJAX，那 25 KB 的 Swup 就走这条较慢的线路。

**PJAX 的真实收益在"后续导航"**：首次加载后站内跳转不再重新下载/解析 CSS/JS，只换内容。但代价见下。

### 6.20 文章与框架「两条管理线」：只做查看层，不拆仓库（2026-10-02 部分完成）

**诉求**：博客仓库的版本管理里，框架改动与文章改动的提交混在同一条时间线上（47 个提交中 36 个是纯框架、6 个两者同时改），想要「文章一条线、框架一条线」。

**做了什么**：只加两个仓库本地 git 别名与一行 `core.quotepath false`，历史与提交方式完全不动 —— `git posts`（文章线）、`git site`（框架线）。**操作与查询速查表在** [`BLOG_GUIDE.md`](../BLOG_GUIDE.md) **§1.5 / §1.6，机制与判定口径在** [`docs/写作与发布.md`](写作与发布.md) **§2.1**（属流程改动），这里只记决策依据，避免两处维护。

**为什么不做物理拆分**（这是本节的重点，防止以后反复讨论）：

| 评估过的物理方案 | 否决原因 |
| --- | --- |
| 文章仓库独立，`source/_posts` 变 submodule | 可行，但每篇文章要在两个仓库各提交一次，且旧历史要么丢失逐次提交、要么上 `filter-repo` 强推两个远程 |
| 单仓库双分支 + worktree + symlink 接回 `source/_posts` | **Hard fail**：Hexo 硬约定 `source/_posts`，接回只能靠 symlink / junction；Windows 侧实测 `core.symlinks=false`，接不回来就是 `hexo g` 找不到文章 |

**关键判断**：本机 WSL 与 Windows **两份克隆都是活跃工作环境**（手册 §1.1），任何依赖链接的目录拆分都会在 Windows 原生侧断掉；而"两条线"的诉求本质是**看得见**，查看层零风险即可满足（用户 2026-10-02 明确选择此路线）。

**完成状态**：⚠️ **部分完成** —— 别名只写进了 WSL 副本 `/home/emberff/blog/.git/config`；`C:\Users\15222\blog` 与任何新建克隆都要按 §1.5 各跑一次配置命令。

**重评触发条件**（满足任一条再启动物理拆分，届时另开小节）：

- 文章量级增长到需要在 GitHub 上按文章粒度分配权限或做 PR 审查；
- 出现博客之外的第二个内容源（多站点共用框架）；
- Windows 侧不再是活跃工作副本（只剩 WSL / Linux 环境，链接限制消失）。

**怎么自查**：

```bash
git config --local --get-regexp '^alias\.'           # 两条别名都在
git config --local --get core.quotepath              # false（保证中文文件名可读）
git posts --oneline | wc -l                          # 文章线条数（应 > 0）
git site  --oneline | wc -l                          # 框架线条数（应 > 0）
git rev-list --count HEAD -- source/_posts           # 触及文章的提交数 = 上面第一个数
```

**状态标记**：⚠️ 环境相关会重现 —— 别名不随 `git clone` / `git pull` 传递，每份新克隆都要重配。
